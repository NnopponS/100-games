# Arcade game-core pilot — protocol locked 2026-11-24 17:33 UTC

**Question.** In this small follow-up to Arcade 100, can a coordinator assigning two independent game cores to parallel workers reach the same held-out correctness as one worker doing both, and how does elapsed wall time differ? This tests a decomposition strategy for deterministic mechanics, not full game shipping, UI polish, economic efficiency, platform scaling, or the three providers named in the historical report.

**Arms and unit.** One paired run, two tasks per arm: Lights Out (#32-inspired) and 2048-style merge (#09-inspired). The single arm is one worker assigned both tasks. The parallel arm is a coordinator using one fresh worker per task, with non-overlapping output paths. The coordinator schedules/collects only, does not implement, test-feedback or fix outputs. The two arms use identical signatures, baseline file bytes, `SPEC.md`, libraries allowed, file-equivalent shared clean work copies and held-out grader. Prompts are matched except assigned task/directory. All workers are fresh, same inherited model/settings unless reported unavailable, not the original study models; no exact telemetry or reproducible decoding parameters assumed. Workers may self-test independently without consulting scoring/outputs. Neither arm is shown another arm’s output; parent does not give pass/fail feedback before freeze.

**Timing and stop.** Start each arm immediately before dispatch of its first worker and stop when all assigned module artifacts are received (most recent completion) or at 360 s, whichever comes first. Record dispatch and observed completion in UTC with seconds and exact tools if available. Record parallel eligible overlap (worker admitted while another not yet reported complete); this is overlapping task lifetimes, not provider token-generation overlap. Record slot waiting before first dispatch separately if known and do not add it to timed arms. Parallel wall time includes dispatch/collection, not coordinator research or grading, just as single wall time excludes benchmark setup and grading. Do not restart either arm or repair candidate results after scoring.

**Primary measures.** Absolute count of independent named acceptance checks passed (20 total; 10 each game). A game is accepted only at 10/10; an arm completes fully at 20/20. Wall time is seconds per two-task arm, with accepted tasks/elapsed minutes as secondary rate. Time ratio is meaningful only when scores and completion match. Also report worker count, observable concurrent eligible workers, per-worker intervals, and human/agent implementation intervention counts. Only report input/output tokens, compute/cost or request throttling with measured telemetry; absent values are “not available.” The resource allocation/compute budget differs: up to two active workers vs. one. Same wall-time limit is not equal token or compute budget.

**Version lock.** `_study/preregister-sha256.txt` records the exact task spec, both stubs, and hidden grader before dispatch; stubs fail 0/20 on Node v24.22.3. Any test change must be separately logged (no model output before correcting grader); no cherry-picked omissions. Order: single then parallel if slots are scarce, with independent fresh workers. A single short paired observation is descriptive, not statistical, does not isolate concurrency from decomposition/focus, and cannot estimate how the original 100-generation project would have performed serially.
